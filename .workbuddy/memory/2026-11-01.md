## ★ 关键新发现：16ms 的 cost.py 读数不可信
- `predict.py` 走 `prep_img_path` → 读 **data600 的 600² 小图**；`cost.py` 走 `list_images` → 读**官方原图**。
- 实测原图：`cxr_first/test` 为 **2500×3052 / 2544×3056**，单张 1.0~1.7MB。
- 按 libjpeg-turbo 解码吞吐估算，20M 像素解码 ≈ 60~150ms，绝无可能总耗时 16ms
  → **10-31 那次 16ms 几乎肯定是用 data600 副本当 pictures_100 测的**，
  真正的「原图解码 + 预处理 + 前向」从未被模拟过。
- 推论：100ms 预算的真实瓶颈是 **JPEG 解码**，不是前向。
  可用 `Image.draft("RGB", (600,600))` 让 libjpeg 直接按 1/4 尺度解码（3056→764），
  解码量降到 1/16 左右，属「优化推理实现」，规则第 7 条允许。
- **两处必须同时改**：predict.py 与 cost.py 要读同一来源，否则一致性核验会挂（当前是两套路径）。

## 第二轮：用户问「有没有别的框架 / 榜上 82 分怎么来的」
- **核心判断：没有魔法框架，只有没拧满的旋钮。** 我们 76.91 是"20 epoch SSL + 12 轮 + 384px + 3 seed soup"，
  相当于穿沙袋跑；82 分队伍大概率在「表征 / 分辨率 / 集成」三处都做满。
- **82 的四种可能归因**（重要，决定我们该以什么为锚）：
  ① 用医学权重（初赛不查，复赛核验会掉）② 无视 500MB/100ms（同上）
  ③ 真·合规做满（可达）④ 测试集伪标签/泄漏（违规）。
- **决定性约束（我复核规则后确认）**：附录 A 要求包内 submission.csv 必须是「历史最高分」那份
  → 若用 2GB 集成刷出 82，则最高分那份无法被合规模型复现，属材料不实（第 11 条）
  → **不能靠"初赛不查"去刷分，必须全程守 500MB/100ms。**
- **四个尚未动过的自由度**（新提出，区别于上一轮）：
  1. **ROI/多裁剪训练**：从原图按肺野/心影/肋膈角裁块当独立样本，数据 ×3~5，强迫关注局部
     （前提：需按 1024² 重新预处理，现有 data600 太小）
  2. **DINO 式自监督替代 SimCLR**（小数据更稳，无需负样本）
  3. **AUC 代理排序损失**（pairwise ranking，直接对齐指标；需类别平衡 batch，风险中等）
  4. **多 stage 特征融合 + 元数据辅助任务**（ViewPosition/PatientOrientation 多任务头）+ **FixRes**（测试分辨率>训练）
- 已明确判定**无效**的方向：label co-occurrence 概率后处理（类内乘常数不改变类内排序 → 对 Macro AUC 无影响）、
  isotonic/rank 校准（单调变换对 AUC 无效）。要利用标签共现必须在**特征层**而非概率层。
- 修正预估：全做上 valid 0.835~0.85 → 平台 80.5~82（即 82 分是可解释、可达的，不需违规）。
